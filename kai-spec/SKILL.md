# kai-spec — 작업 지침서 작성 표준

> 이 스킬은 **Opus(또는 상위 추론 모델)가 지침서를 쓸 때** 발동한다.
> 산출된 지침서는 Sonnet·`kai-task-run` 워커가 받아 **빠짐없이** 구현한다.

## 0. 왜 존재하는가 (근본 원인)

Sonnet·워커는 **지침서에 적힌 것만** 충실히 수행한다.
지침서가 데이터 흐름의 한 토막만 담으면 나머지를 빠뜨리는 것은
**능력 문제가 아니라 필연**이다.

빠짐의 정체는 거의 항상 **배선(wiring) 누락**이다 —
끝점(데이터 정의처, 소비처)은 적혀 있으나, 둘을 잇는 **호출(producer 트리거)**이 빠진다.

> 실패 사례(실제): "store에 필드 추가 ✅" + "drawer를 동적화 ✅" 는 적었으나,
> 그 store를 **채우는 `hydrate()` 호출 지점**을 지침에서 빠뜨려 → 화면이 끝내 안 됨.
> 데이터와 소비자는 있었으나 **그 둘을 잇는 선**이 없었다.

이 표준의 1번 규칙이 그것을 강제로 발견하게 한다.

---

## 1. 절대 원칙 (4가지)

1. **추측 금지 · 추적 필수.** 지침서를 쓰기 전, 작성자가 전체 코드 경로를
   **실제로 열어 추적**한다. "호출되겠지"라고 가정하지 않는다.
   확인 못 한 단계는 단정하지 말고 `⚠️확인필요`로 표기한다.
2. **끝점이 아니라 연결선을 적는다.** 데이터를 *누가 채우고*, 그 채우는 호출이
   *실제로 어디서 실행되는지*를 명시한다. (§3 배선 체크)
3. **산문 금지.** Sonnet이 하나씩 체크하도록 `- [ ] {파일경로}: {변경} → {검증}` 형식.
   줄글로 풀어쓰면 또 빠뜨린다.
4. **짧게 유지.** 한 페이지로 돌릴 수 있는 체크리스트. 400줄 지침서는 똑같은 이유로 건너뛰어진다.

---

## 2. 작성 절차 (Opus가 순서대로 수행)

### 1단계 — 흐름 추적 (코드를 실제로 연다)

변경이 통과하는 **모든 레이어를 경로째** 추적한다. 일반화된 양식:

| 스택 | 추적할 경로 |
|---|---|
| **프론트(Angular)** | API client/service → state store(signalStore) → component `.ts` → template `.html` |
| **백엔드(.NET)** | controller → service → repository → entity → DB(테이블/마이그레이션) |

각 링크를 **Read/Grep으로 직접 확인**한다. 탐색 범위가 넓으면 `Explore`/`general-purpose`
서브에이전트를 병렬로 띄워 경로를 채운다(Sonnet 기본, 모호하면 Opus).

### 2단계 — 배선 지점 식별 (가장 잘 빠지는 곳)

아래 5칸을 **반드시 모두** 채운다. 빈 칸이 있으면 지침서는 미완성이다.

- [ ] **데이터 정의처** — 타입/필드/엔드포인트가 어디에 정의되는가
- [ ] **데이터 생산처** — 그 데이터를 채우는 호출(`hydrate`/`load`/`fetch`/`reload`)은 어디 있는가
- [ ] **생산 호출의 트리거 지점** ← ★ 여기가 직전 실패 지점. 그 호출이 *실제로 실행되는* 곳(`ngOnInit`/`effect`/라우트 진입/구독)을 지정했는가
- [ ] **데이터 소비처** — 어느 component/template이 그 데이터를 쓰는가
- [ ] **횡단 규칙** — CUD면 toast, 위험작업이면 confirm, 신규 문구면 i18n(ko/en/zh) — 누락 없는가

### 3단계 — 파일별 변경표 작성

체크박스 + 파일경로 + 검증. (§4 템플릿)

### 4단계 — 검증 가능한 DoD 작성

목표("상태를 동적으로")가 아니라 **관측 가능한 종료 상태**로 쓴다.
- ❌ "결제 상태를 동적으로 표시한다"
- ✅ "`/payments` 진입 → 액션 클릭 → 드롭다운이 하드코딩이 아닌 **DB 상태 13개**를 표시한다"

### 5단계 — 자체 시험 (유일한 합격 기준)

완성된 지침서에 대고 스스로 묻는다:

> **"이 지침서만 보고 구현하면, 흐름의 어느 한 지점이라도 빠뜨릴 수 있는가?
>   특히 §2의 '생산 호출 트리거 지점'을 빠뜨릴 수 있는가?"**

빠뜨릴 수 있으면 아직 미완성이다. 빠뜨릴 수 **없을 때까지** 보강한다.
(이 시험은 직전 hydrate 누락을 강제로 잡아낸다 — 그것이 이 표준의 존재 이유다.)

### 6단계 — advisor 능동 검토 (불분명·고위험 시 필수)

지침서에 **조금이라도 불분명한 지점**(배선이 안 풀림, 필드 출처 불명, 상태 전이 모호)이 있거나,
**새 기능 · 리팩토링 · 외부 통합 · DB 스키마 · 인증/결제/보안** 작업이면,
완성된 지침서 초안을 `advisor` 서브에이전트(Opus, `Agent(subagent_type:"advisor")`)에게 넘겨 5섹션 검토를 받는다.

- **§5 🔴(지금 반드시)** 항목 → 지침서에 **반드시 반영** (놓친 배선·엣지케이스·규칙 위반).
- **🟡(함께 하면 좋음)** → 같은 흐름이면 체크리스트에 추가.
- **🟢(차후 고려)** → "차후 과제" 절로 분리(스코프 크리프 방지).

이 단계가 **"작성자(Opus)조차 미처 생각지 못한 빠짐·오류·개선"**까지 메우는 마지막 그물이다.
불분명을 추측으로 덮지 않는다 — 반드시 advisor로 확인하고 진행한다.

---

## 3. 산출물

- 기본 위치: `.plan/{기능명}.md` (또는 사용자가 지정한 경로)
- 다중 에이전트 작업 큐에 넣으려면, 완성된 스펙을 `/kai-task-add`로 등록한다.
- 이 스킬은 **지침서 파일만 산출하고 종료**한다 — 구현·빌드·테스트는 하지 않는다.

---

## 4. 지침서 템플릿 (이 형식으로 출력)

```markdown
# {기능명} 작업 지침서

## 목표 (한 줄)
{무엇을 달성하는가}

## 흐름 추적 (확인 완료)
{API → store → component → template, 또는 controller → service → repo → entity}
각 단계 옆에 실제 파일경로:line 명시. 확인 못 한 곳은 ⚠️확인필요.

## 배선 체크 (5칸 모두 채움)
- 데이터 정의처: `path:line`
- 데이터 생산처: `path:line` (예: store.hydrate())
- ★ 생산 호출 트리거: `path:line` (예: view-payments.ts ngOnInit에서 hydrate() 호출 — 현재 없음 → 추가)
- 데이터 소비처: `path:line`
- 횡단 규칙: toast/confirm/i18n 해당 여부

## 파일별 변경 (체크박스로 구현)
- [ ] `path/to/file.ts`: {정확한 변경} → 검증: {어떻게 확인}
- [ ] `path/to/other.html`: {정확한 변경} → 검증: {어떻게 확인}
- [ ] ... (배선 연결선 항목을 빠뜨리지 말 것)

## 완료 조건 (DoD — 관측 가능)
- [ ] {URL 진입 → 동작 → 관측되는 결과}
- [ ] 빌드 통과 / 콘솔 에러 없음
- [ ] (해당 시) toast·confirm·i18n 3종 locale 반영

## 구현 중 불분명 시 (구현자 필독)
이 지침서대로 구현하다 **조금이라도 불분명·모호한 지점**이 나오면, 추측으로 진행하지 말고
`advisor` 서브에이전트(Opus, `Agent(subagent_type:"advisor")`)를 호출해 확인·추가조언을 받은 뒤 진행한다.
advisor §5 🔴 항목은 빠짐없이 반영한다.
```

## 5. 사용 예

```
/kai-spec verida-ops 결제 화면의 상태 드롭다운을 DB의 동적 상태 목록으로 표시
```

→ Opus가 `verida-ops`의 API·StatusCatalogStore·view-payments·drawer 경로를
실제로 추적하고, `hydrate()` 트리거 누락 같은 배선 구멍을 §2에서 강제로 드러낸 뒤,
체크박스 지침서를 `.plan/payments-status-dropdown.md`에 산출한다.
