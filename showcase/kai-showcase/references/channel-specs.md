# 채널 규격 — 어디에 올릴 것이며, 그쪽은 무엇을 보는가

> 2026-09 리서치 실측. 수치를 임의로 바꾸지 말 것 — 근거 URL 은 맨 아래.

## 1. 리크루터 · 채용 담당자 (케이스 스터디)

| 그들이 하는 것 | 우리가 맞추는 것 |
|---|---|
| **깊이 > 넓이** — 얕은 10개보다 잘 다듬은 3개를 본다 | 프로젝트 하나를 끝까지 판다 |
| **"GitHub 은 코드를, 포트폴리오는 판단을 보여준다"** — 저장소는 거의 읽지 않는다 | 코드 링크가 아니라 **결정과 근거**를 쓴다 |
| 아키텍처 도면 + **레이어마다 트레이드오프 하나** | "왜 Postgres 인가 · 왜 큐인가 · 왜 SSR 인가" 를 각각 한 문장 |
| 문제 진술이 맨 앞 · 측정 가능한 결과가 맨 뒤 | Problem 으로 열고 Impact 로 닫는다 |

**트레이드오프가 full-stack 을 증명한다.** 기술 나열(full-list)과 갈리는 지점이 여기다.

## 2. Upwork (클라이언트)

- **8초 스캔.** 찾는 것은 단 하나 — *"내 문제를 전에 풀어봤나"*
- 항목은 프로젝트 설명이 아니라 **미니 케이스 스터디**로 쓴다
- 스킬 하나당 **3~5개**. 제안서에 붙일 때는 **3종**: ① 그 일과 가장 닮은 것 ② 결과가 뚜렷한 것 ③ 과정을 보여주는 것
- **전 필드를 채운다** — 제목 · 역할 · 설명 · 스킬 태그 · 미디어 · 썸네일. 빈 칸은 그대로 손해
- 제목은 **구매자의 언어**로. `OneVoice 통역 서버` ❌ → `Real-time sermon interpretation for a multilingual church` ✅

### ⚠️ 실제 입력 칸 규격 (2026-09-13 화면에서 직접 잼)

**이 한도를 넘기면 Upwork 화면에서 그대로 못 쓴다.** 초안을 쓸 때부터 맞춰서 쓴다.

| 칸 | 한도 |
|---|---|
| Project title | **70자** |
| Your role | 100자 (선택) |
| Project description | **600자** |
| Skills and deliverables | **정확히 5개까지** |
| 본문 콘텐츠(이미지·글 블록·영상·웹링크·PDF·음성) | **최소 1개 필수** |
| 글 블록 본문 | 약 1,000자 |

- **썸네일(대표 이미지)이 없으면 Publish 도 "초안 저장"도 잠긴다.** 기술 5개가 비어도 초안 저장이 막힌다.
- 에이전트에게는 파일 업로드 도구가 없는 경우가 많다 → **글은 에이전트가 채우고 이미지는 사람이 넣는 분업**을 전제로 산출물을 쓴다.

### 설명 칸은 사람이 읽는다 — 기술 용어를 넣지 않는다

2026-09-15 사용자 지적: *"이게 사람이 읽는 거라서, 너무 기술적이거나 그러면 안 돼."*
Upwork 에서 글을 읽는 쪽은 대개 **비기술 사업주**다. 설명 칸에는 **무슨 문제를 누구에게 풀어 줬는지**만 쓴다.

- ❌ `오디오를 100ms 프레임으로 잘라 raw WebSocket 으로 흘려보내고…`
- ✅ `말하는 이는 그냥 말합니다. 나머지는 휴대폰으로 QR 을 찍어 제 나라 말로 따라 읽습니다. 설치할 것도 계정도 없습니다.`

기술 세부는 **버리지 말고 자리를 옮긴다** — 본문 글 블록에 `For the technically minded` 같은 제목으로 따로 둔다.
보고 싶은 사람만 보게 하면 두 독자를 모두 잡는다.

## 3. LinkedIn (캐러셀)

| 항목 | 값 |
|---|---|
| 크기 | **1080 × 1350 px (4:5 세로)** — 모바일 피드 점유가 가장 크다 |
| 장수 | **6~10장** — 깊이와 집중력의 균형점 |
| 1장 | **훅** — 한 줄 주장 + 대표 도면 |
| 마지막 | **CTA** — 무엇을 해달라는지 한 줄 |
| 알고리즘 | **체류시간(dwell time)** 이 핵심 신호 → 여러 장이 유리한 이유 |
| 디자인 | 장마다 **같은 레이아웃·같은 브랜딩**. 들쭉날쭉하면 넘기다 만다 |

**캐러셀은 영어만 쓴다** — 1080 폭에 두 언어를 넣으면 글자가 작아져 4:5 의 이점이 사라진다.

### 8장 기본 구성 (프로젝트에 맞춰 조정)
1. 훅 — 무엇을 만들었나 (한 줄) + 대표 도면
2. 문제 — 누구의 어떤 고통이었나
3. 제약 — 예산·시간·기술·조직의 한계
4. 접근 — 택한 구조 (기술 도면)
5. 핵심 결정 — 트레이드오프 1~2개 ("왜 A 가 아니라 B")
6. 고비 — 막혔던 지점과 넘은 방법
7. 결과 — 수치 또는 정성 결과
8. CTA — 연락처 · 무엇을 도울 수 있는지
