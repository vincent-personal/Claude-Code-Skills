# task-add — 작업 체크리스트 추가 스킬

## 역할

사용자가 지시한 작업을 **직접 실행하지 않고**, 현재 프로젝트의 `docs/check-list.md`에
번호가 증가하는 체크 항목으로 추가한다.
**영향 파일을 의무적으로 기록**하여 다중 에이전트 환경에서 파일 충돌을 방지한다.

---

## ⚡ 실행 절차

### Step 0 — 프로젝트 루트 탐지

```bash
git rev-parse --show-toplevel 2>/dev/null || pwd
```

이 결과를 `PROJECT_ROOT`로 사용한다.
체크리스트 경로: `{PROJECT_ROOT}/docs/check-list.md`

---

### Step 0-A — 파일 없으면 표준 템플릿으로 신규 생성

파일이 존재하지 않으면 `docs/` 디렉터리를 생성하고 아래 4-틸드(`~~~~`) 펜스로 감싼 **전체 템플릿**으로 파일을 만든다.
`{YYYY-MM-DD}` 는 오늘 날짜로 치환한다.
펜스(`~~~~markdown` / `~~~~`) 자체는 파일에 포함시키지 않는다.

~~~~markdown
# 작업 체크리스트

> 생성: {YYYY-MM-DD}
> 본 파일은 /task-run 스킬이 자율 실행하며 관리한다.

---

## 🤖 자율 실행 원칙 (최상위 규칙)

**이 에이전트는 사용자 인풋을 기다리지 않는다. 막히면 멈추지 말고 판단해서 진행한다.**

- 모호한 요구사항 → 가장 합리적인 해석으로 진행 + 결정 근거 기록
- 여러 옵션 → 프로젝트 컨벤션에 가장 맞는 것 자동 선택 + 사유 기록
- 충돌/이슈 → 자체 판단으로 해결 시도 → 실패 시에만 `🚨 BLOCKED` 마킹
- "확인이 필요합니다" / "어떻게 할까요?" 같은 문구 출력 금지

**"실수해도 좋으니 멈추지 마라"** — 잘못된 구현은 다음 루프에서 수정 가능. 멈춰 있는 작업은 가치 0.

---

## 작업 상태 표시 (4단계)

- `- [ ]` — 미시작 (기본값)
- `- [~]` — 작업중 (선점됨 — 다른 에이전트 착수 금지)
- `- [x]` — 작업완료 (10개 이상 누적 시 자동 아카이브)
- `- [!]` — 자체 판단으로 진행했으나 사후 확인 권장

## 자동 아카이브 정책

`- [x]` 항목이 **10개 이상**이면 task-add/task-run 실행 시 자동으로 가장 오래된 것부터 `check-list-done.md` 로 이동.
**최근 5개**는 Tier 2 자문 참조용으로 본 파일에 보존.
사용자가 `/task-clear` 를 까먹어도 컨텍스트가 무한히 부풀지 않도록 하는 안전장치.

---

## 작업 항목 표준 포맷

```
- [ ] **#N** — {제목}.
  - **영향 파일**: path/to/file1.ts, path/to/file2.scss
  - {세부 설명 1}
  - {세부 설명 2}
```

**영향 파일은 의무 필드**다. 없으면 task-run 충돌 검사가 동작하지 않는다.
파일 경로는 PROJECT_ROOT 기준 상대경로로 적는다.

---

## ⚠️ 필수 규칙 1 — 사용자 작업 잠금 확인

`{PROJECT_ROOT}/.claude/user.lock` 파일이 존재하면 사용자가 직접 작업 중이다.
백그라운드 루프 에이전트는 이 파일이 있으면 즉시 종료한다.

```bash
if [ -f .claude/user.lock ]; then
  echo "BLOCKED: 사용자 작업 중 — 다음 루프에서 재시도"
  exit 0
fi
```

---

## ⚠️ 필수 규칙 2 — 작업 상태 선점 + 타임스탬프

작업을 시작하기 전에 반드시 해당 항목을 다음 형식으로 변경한다:

```
- [~] **#N** — 제목. (선점: YYYY-MM-DD HH:MM)
```

이미 `- [~]` 인 항목은 다른 에이전트가 작업 중이므로 절대 건드리지 않는다.
선점 Edit이 실패하면 다음 미시작 항목으로 진행한다.

---

## ⚠️ 필수 규칙 3 — 좀비 선점 복구 (30분 timeout)

`- [~]` 항목의 선점 타임스탬프가 **현재 시각 - 30분 이전**이면 좀비로 간주.
좀비를 발견하면 `- [~]` → `- [ ]` 로 되돌리고 (선점 타임스탬프 제거) 정상 선점 절차 수행.

```bash
# 현재 시각 (분 단위 비교용)
date +%Y%m%d%H%M
```

---

## ⚠️ 필수 규칙 4 — 영향 파일 충돌 검사

작업 항목 선택 전:
1. 현재 모든 `- [~]` 항목의 **영향 파일** 목록을 수집 (locked_files 집합)
2. 후보 `- [ ]` 항목의 영향 파일과 locked_files의 교집합 확인
3. 교집합이 비어있지 않으면 → 해당 후보 skip, 다음 후보로
4. 모든 `- [ ]` 후보가 충돌하면 → "충돌로 진행 불가" 보고 후 종료

**영향 파일이 명시되지 않은 항목은 충돌 검사 불가** → Tier 3로 간주하고 advisor에게 파일 식별 요청 후 본 항목 갱신.

---

## ⚠️ 필수 규칙 5 — 작업 분류 (Tier)

착수 전 작업 유형을 분류하고 해당 규칙에 따라 처리한다. **판단이 애매하면 한 단계 위 Tier로.**

### 🟢 Tier 1 — advisor 생략 (단독 처리)
- typo, 포맷팅, 주석, import 정리
- 1~5줄 미세 수정 (로직 변경 없음)
- 변수명/메서드명 리네이밍
- `[skip-advisor]` 태그가 있는 항목

### 🟡 Tier 2 — 기존 패턴 참조 (advisor 생략 가능)
- 동일/유사 작업의 advisor 자문이 7일 이내 존재
- 같은 파일에 대한 추가 수정
- 유사 패턴 반복 작업

### 🔴 Tier 3 — advisor 호출 필수 (Opus 계획 → Sonnet 구현)
- 새 기능/모듈 구현
- 기존 코드의 구조적 변경
- 외부 라이브러리/서비스 통합
- DB 스키마 변경
- 인증/결제/보안 관련 코드

---

## ⚠️ 필수 규칙 6 — advisor 호출 절차 (Tier 3 전용)

1. `advisor` 에이전트(Opus 모델) 호출
2. 전달 정보: 작업 항목 본문 / 관련 파일 경로 / 프로젝트 제약 조건
3. advisor 응답의 "영향 범위"에서 새로 발견된 파일은 본 체크리스트 항목의 **영향 파일**에 즉시 append
4. 응답 수신 후 **즉시 구현 착수** (추가 승인 불필요)

---

## ⚠️ 필수 규칙 7 — 워크트리 절대 금지

> **이 규칙을 어기면 수십 개의 수정 사항이 분실될 수 있다. 실제로 발생한 사고다.**

- ❌ `git worktree add` 로 워크트리 생성 금지
- ❌ `cp` / `rsync` 등으로 워크트리 ↔ 원본 파일 동기화 금지
- ✅ 모든 코드 수정은 git 루트 아래 원본 파일에서만 수행

파일 수정 전 `realpath` 또는 `cd $(dirname FILE) && pwd -P` 로 실제 경로가
`PROJECT_ROOT` 하위인지 검증한다.

---

## ⚠️ 필수 규칙 8 — 빌드/Git 절차

> 이 섹션을 프로젝트에 맞게 수정한다.

### 빌드 직렬화 (build lock)

```bash
BUILD_LOCK="{PROJECT_ROOT}/.claude/build.lock"

# 다른 에이전트가 빌드 중이면 최대 5분 대기
TIMEOUT=300
while [ -f "$BUILD_LOCK" ] && [ $TIMEOUT -gt 0 ]; do
  sleep 5
  TIMEOUT=$((TIMEOUT - 5))
done

# 락 획득 후 빌드
touch "$BUILD_LOCK"
trap "rm -f $BUILD_LOCK" EXIT
cd {PROJECT_ROOT} && npm run build
```

빌드 실패 시 자체 수정 시도 (최대 3회) → 3회 실패 시 `🚨 BLOCKED`.

### Git 커밋·푸시 (선택)

```bash
# 충돌 방지를 위해 pull --rebase 후 push
cd {PROJECT_ROOT}
git pull --rebase
git add {수정한 파일들}
git commit -m "feat(#N): {제목}"
git push
```

여러 에이전트가 동시에 push 시도하면 rebase 실패 가능 → 재시도 (최대 3회).

1. **멈추지 마라** — 막히면 자체 판단으로 진행

_작업 완료 시: `- [~]` → `- [x]` 로 변경하고 완료 내용을 기록함._
~~~~

---

### Step 1 — check-list.md 읽기

파일을 Read하여 다음을 파악한다:
- **현재 최고 작업 번호** (`**#N**` 패턴의 최댓값 N, 없으면 0)
- **작업중 항목** (`- [~]`): 절대 수정 금지
- **미시작 항목** (`- [ ]`): 새 작업과 합칠 수 있는지 확인
- **완료 항목** (`- [x]`): 개수 파악 (다음 단계 자동 아카이브용)

---

### Step 1-Z — 완료 항목 자동 아카이브 (컨텍스트 누적 방지)

`- [x]` 항목 개수가 **10개 이상**이면, 가장 오래된 것부터 자동 아카이브하여 **최근 5개만 남긴다**.

#### 절차

1. 파일 내 `- [x]` 항목들을 등장 순서대로 나열 (오래된 것이 위)
2. 개수 ≥ 10 이면 → 위에서부터 `(개수 - 5)` 개를 추출
3. 추출한 항목들(세부 항목 포함)을 `{PROJECT_ROOT}/docs/check-list-done.md` 에 append
   - 파일 없으면 헤더 생성 후 추가
   - 형식: `## {YYYY-MM-DD} 자동 아카이브` 섹션 아래
4. `check-list.md` 에서 추출한 항목 제거
5. 콘솔에 "🗄️ 완료 항목 N개 자동 아카이브" 보고

**절대 건드리지 않을 것:**
- `- [ ]`, `- [~]`, `- [!]` 항목
- 파일 상단 규칙/원칙 섹션
- 최근 5개의 `- [x]` (Tier 2 자문 참조용으로 보존)

### Step 1-A — 미시작 항목과 접목 가능 여부 확인

미시작(`- [ ]`) 항목 중 새 작업과 **동일 파일·동일 컴포넌트·동일 기능 범위**인 항목이 있으면:
- 신규 항목으로 추가하는 대신 **해당 기존 항목에 세부 설명을 병합**한다.
- 병합 시 기존 항목 번호를 유지하고 세부 항목만 추가한다.
- **영향 파일은 두 항목의 합집합으로 갱신**한다.
- 완전히 다른 범위면 별도 항목(`#N+1`)으로 추가한다.

---

### Step 2 — 영향 파일 식별 (의무)

사용자 설명을 분석하여 작업이 수정/생성할 파일의 **초안 목록**을 만든다.

1. 설명에 파일 경로가 명시되어 있으면 그대로 사용
2. 컴포넌트/기능 이름만 있으면 `Glob`/`Grep` 으로 후보 파일 탐색
   - 컴포넌트명, 라우트명, 서비스명, API 엔드포인트 등 키워드 다각도 검색
   - 직접 수정 파일 외에 **import/의존 관계**로 연결된 파일도 후보에 포함
3. 탐색 후에도 불명확한 파일은 `?` 표시 후 Step 2-A 에서 advisor에게 확정

**최소 1개 이상의 영향 파일이 반드시 기록되어야 한다.**
경로는 PROJECT_ROOT 기준 상대경로.

---

### Step 2-A — Tier 판단 및 advisor 호출

아래 기준으로 Tier를 판단한다. **애매하면 한 단계 위 Tier로.**

| Tier | 조건 | advisor 호출 |
|---|---|---|
| 🟢 1 | typo·포맷·주석·import 정리·1~5줄 미세 수정 | ❌ 생략 |
| 🟡 2 | 동일 패턴 반복·같은 파일 추가 수정·`[skip-advisor]` 태그 있는 항목 | ❌ 생략 |
| 🔴 3 | 새 기능/모듈·구조 변경·외부 서비스 통합·DB 스키마·인증/결제/보안·Step 2에서 `?` 파일이 **2개 이상**인 경우 | ✅ **필수** |

> **주의:** "영향 파일 개수"는 Tier 기준에서 제외한다. 파일이 많더라도 동일 패턴 반복이면 Tier 2.

#### Tier 3 — advisor 호출 절차

`advisor` 에이전트(Opus 모델)를 호출하며, 아래 정보를 전달한다:

```
[작업 설명]
{사용자 원문 그대로}

[초안 영향 파일]
{Step 2에서 찾은 파일 목록 (? 표시 포함)}

[요청]
1. 빠진 영향 파일이 있는지 확인하고 완전한 목록을 제시해줘.
2. 이 작업의 구체적인 구현 방안을 단계별로 기술해줘.
3. 놓치기 쉬운 엣지 케이스나 주의사항을 알려줘.
```

advisor 응답을 수신한 후:
- **영향 파일**: advisor가 추가한 파일을 초안 목록에 병합, `?` 표시 제거
- **구현 방안**: advisor의 단계별 구현 방안을 Step 3 작업 설명에 반영
- **주의사항**: advisor가 언급한 엣지 케이스를 세부 항목에 추가
- **advisor 호출 완료 마커**: 항목 제목 끝에 `[advisor:done]` 태그를 추가한다.
  - 예: `- [ ] **#5** — 로그인 폼 구현. [advisor:done]`
  - task-run이 이 태그를 보고 advisor 재호출을 생략한다.

---

### Step 3 — 작업 설명 작성

사용자 원문과 **advisor 응답(Tier 3인 경우)**을 바탕으로 **명확하고 실행 가능한** 작업 설명을 작성한다.

**작성 원칙:**
- 무엇을(What): 어떤 파일/컴포넌트/기능을 수정하는가
- 어떻게(How): 구체적인 구현 방법 (Tier 3이면 advisor의 단계별 방안을 그대로 세부 항목으로 기술)
- 주의사항(Note): 연관 파일, 엣지 케이스, 확인 필요 항목 (advisor 결과 포함)

**세부 항목 수 기준:**
- Tier 1: 최소 2개 (영향 파일 + 1줄 설명)
- Tier 2: 최소 3개
- Tier 3: 최소 5개 (영향 파일 + 구현 단계 3개 이상 + 주의사항 1개 이상)

---

### Step 3-A — 화면 작업 여부 감지

아래 조건 중 하나라도 해당하면 **화면 작업**으로 판단하고, 세부 항목에 다음 지침을 추가한다:

**감지 조건:**
- 영향 파일 확장자에 `.html`, `.scss`, `.css`, `.component.ts` 포함
- 작업 설명에 "화면", "UI", "컴포넌트", "뷰", "스타일", "레이아웃", "페이지", "모달", "드로어", "폼", "버튼", "카드", "테이블" 등 UI 키워드 포함

**세부 항목에 추가할 지침:**
```markdown
  - **[화면 작업 필수]** task-run 시 아래 스킬을 순서대로 활용할 것:
    1. `/browse` 또는 Playwright MCP — 구현 전 현재 화면 상태 확인 및 구현 후 브라우저 검증
    2. `ecc:docs-lookup` 또는 Context7 — 사용 중인 UI 라이브러리/프레임워크 최신 API 레퍼런스 확인
    3. `design-review` 또는 `ecc:frontend-design` — 구현 후 디자인 일관성 검토
```

---

### Step 4 — check-list.md에 항목 추가

`# 작업 목록` 섹션 아래 (파일 맨 아래)에 다음 형식으로 추가한다:

```markdown
- [ ] **#N+1** — {한 줄 요약 제목}.
  - **영향 파일**: path/to/file1.ts, path/to/file2.scss
  - {세부 설명 1}
  - {세부 설명 2}
```

**형식 규칙:**
- 번호는 현재 최댓값 + 1
- 첫 줄: `- [ ] **#N** — 요약 제목` (마침표로 끝냄)
- **첫 번째 세부 항목은 반드시 `- **영향 파일**: ...` 형식** (task-run이 파싱)
- 세부 항목: 들여쓰기 2칸 + `- {내용}` (최소 영향 파일 포함 2개 이상)
- 체크박스는 반드시 빈 상태 `[ ]` 유지

---

### Step 5 — 완료 보고

추가한 항목 번호, 요약, 영향 파일 목록을 사용자에게 보고한다.
신규 파일을 생성했다면 "체크리스트를 새로 생성했습니다." 도 함께 보고한다.

## Red Lines (절대 금지)

- ❌ 작업을 직접 실행하거나 코드를 수정하는 행위
- ❌ 체크박스를 `[x]`로 표시하는 행위
- ❌ `- [~]`(작업중) 항목 수정·삭제·병합
- ❌ 번호 순서 건너뛰기 (항상 max+1)
- ❌ **영향 파일 없이 항목 추가** (충돌 검사 무력화)
- ❌ 세부 내용 없이 제목만 추가
